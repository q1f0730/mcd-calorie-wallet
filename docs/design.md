# 设计思路 · 卡路里钱包

## 为什么做它

近 700 份参赛作品里，"根据口味推荐套餐""多人拼单""MBTI 点餐"是红海——它们共享同一个范式：**输入偏好 → 输出推荐**。但没有人回答一个更真实的问题：

> **"我今天还剩多少热量额度？在这些额度里我能吃什么？"**

减脂期的人不是不知道自己喜欢吃什么，而是不确定"吃了这份套餐，本周的预算还够不够"。卡路里钱包把点餐从"猜你喜欢"变成"预算求解"。

## 建模

点餐 = 背包问题（Knapsack）：

- **容量**：本餐热量上限（硬约束，超了直接无解/降级）
- **物品体积**：商品 kcal（来自 MCP 实时营养数据）
- **物品收益**：用户偏好分
- **求解目标**：上限内收益最大化，并展示"kcal/元"热量单价

菜单规模几十件，采用"主件枚举 + 贪心填充"，结果可解释、可复现，不引入重量级求解器依赖。

## 关键产品决策

1. **硬约束哲学**：超预算绝不"差不多就行"。要么降级（砍品类、换 0 卡饮料），要么明说"吃不起"。这是与所有推荐器的本质区别。
2. **数据洁癖**：kcal 只来自 MCP 实时返回，缺失即剔除。绝不凭模型记忆估算营养——错 50 kcal 对减脂用户就是灾难。
3. **余额预警**：本餐吃完后如果剩余额度 < 一个标准正餐，主动预警"本周后面几餐要清淡了"。把钱花光之前告诉你钱包快空了，这才配叫"钱包"。
4. **安全边界**：默认只读，下单前必须逐字确认"确认下单"。

## 边界与不做的事

- 不构成医疗/营养建议（见 CONTEST_DECLARATION.md）
- 不做连续多天的膳食规划（一餐求解已足够锋利，多天规划是另一个产品）
- 不猜门店营业状态，营业信息以 MCP 返回为准
